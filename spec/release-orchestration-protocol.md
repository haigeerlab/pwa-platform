# 规格：release-orchestration-protocol

## 目标

定义外部发布系统如何为 PWA 发布采集可信事实、调用 build-verifier、串行保存发布历史，并仅在生产成功后更新 identity baseline。该规格使运行手册的门禁可执行，但不把部署平台或凭据模型锁进 PWA 平台仓库。

## 范围

本仓库交付协议、记录模板和验证示例；实际发布器、CDN/API 客户端、密钥、数据库和 CI 集成由基础设施团队在外部系统实现。

每个部署槽位必须拥有互斥的发布线，键至少由 `appId`、`origin`、`environment` 与稳定槽位名确定。一次发布记录至少保存：

- 候选 `PwaPlan`、构建标识、产物绝对路径清单与评估时刻；
- 已观测响应头、完整的同一发布线历史计划与发布时间、当前可用资产路径；
- `verifyRelease` 报告、门禁覆盖结果及 CI、浏览器、原生安装、恢复演练的证据引用；
- 首次发布或身份迁移的审批引用；成功后的生产发布时间。

状态顺序为：`prepared`（事实已采集）→ `verified`（机器检查和证据齐全）→ `deployed`（生产成功）→ `recorded`（历史与基线写入完成）。任一失败保持非成功状态；同一槽位不得并行推进两个发布。

首次生产发布必须显式记录 `verify.baseline-missing` 和平台负责人批准，不能仅省略 baseline 检查。共享源子应用还必须向 `verifyRelease` 传入实际线上根计划。

## 命令

本模块不提供仓库内可执行发布命令。外部系统必须在其受控环境中运行：

```text
verifyRelease(candidatePlan, collectedFacts)
verifyReleaseGateCoverage(report, requiredChecks)
```

并保存可复查但不含令牌、响应体、用户数据或私有资产 URL 的记录。

## 测试策略

- 本仓库对协议模板、相对链接和与 ADR-0014/0024、运行手册、RACI 的一致性做静态核验。
- 外部系统必须进行合约测试：缺一个必需事实、缺一个报告检查、基线缺失无批准、乱序历史、并发发布和生产失败后误写 baseline 均不得进入 `recorded`。
- 每个实际生产环境在首次接入时做一次受控演练，保留门禁输出与回滚记录。

## 边界

- **始终**：外部输入在采集边界验证；一槽位一次发布；只在生产成功后写历史和基线；证据记录脱敏。
- **先询问**：选定部署提供商、授权凭据、改变记录保留期限、首次发布或身份迁移放行。
- **禁止**：把凭据或发布状态加入 PWA 包、从失败发布更新 baseline、将缺失报告检查解释为通过。

## 验收标准

1. 外部实现可从记录中重放本次门禁的事实与结论。
2. 正常发布包含所有机器必需检查并通过；首次发布例外有可追溯人工批准。
3. 成功发布的计划和时间可供 ADR-0024 的完整历史输入使用。
4. 平台仓库未新增网络部署代码、凭据或持久状态。

## 开放问题

- 具体部署托管提供商、发布记录存储和 CI 运行器由基础设施团队决定后，另在其系统中建模；不在此规格猜测。
