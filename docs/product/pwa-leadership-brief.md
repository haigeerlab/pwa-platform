# PWA 决策简报：让网站具备 App 式回访能力

> 读者：业务负责人、产品负责人、管理层  
> 目的：判断是否建设 PWA 平台，以及第一阶段应投入什么、不投入什么。

## 请先看结论

PWA 是一种让网站“可安装、像 App 一样打开”的方式。它适合高频回访、弱网访问和需要提升触达效率的业务；不适合承诺离线观看直播、永久后台运行或完全替代原生 App。

- `qwzb.live` 已经实现了基础 PWA：可在 Chrome 中安装为“198直播”，并以独立应用窗口打开。该结论已在真实浏览器中复核。
- 但它主要解决了“装得上、打开像 App”：断网后重新打开会完全白屏；系统通知实际送达、稳定更新和缓存治理也未得到验证。
- 我们的机会不在于复制一个安装按钮，而在于把 **弱网可靠、更新不打断业务、数据不被错误缓存、上线可验证** 做成各业务可复用的平台能力。

建议：先建设一个可在单个业务试点落地的 PWA 基线；系统通知、离线提交、域名灾备等按业务价值后置，不与第一期绑定。

## PWA 能给业务带来什么

| 能力 | 用户感受 | 业务价值 | 需要注意 |
|---|---|---|---|
| 安装到桌面 | 像打开 App 一样打开网站 | 降低回访门槛、加强品牌入口 | 用户仍需要有安装意愿 |
| 弱网与离线提示 | 网络差时不白屏，知道下一步怎么做 | 减少流失和客服压力 | 直播、支付、私有信息不能为了离线而缓存 |
| 安全更新 | 有新版时在合适时机更新 | 少发生“看直播/填表时被刷新” | 需要发布与回滚流程 |
| 系统通知（Push，可选） | 未打开页面也能收到提醒 | 用于赛程、消息和运营召回 | 须经用户授权，不能保证必达或过度打扰 |
| 统一治理 | 不同业务按同一安全标准接入 | 降低重复开发和线上事故 | 需要先建设公共平台能力 |

## 对标：`qwzb.live`

### 已确认

- Chrome 中有“安装‘198直播’”入口。
- 安装后成为独立应用，可脱离普通浏览器标签页启动。
- 联网状态下可加载首页与实时赛事内容。

### 尚未证实或明显不足

- **断网后重新打开会完全白屏（已确认）**，没有给用户恢复路径或友好提示。
- 用户同意通知后，消息能否稳定送达与跳转。
- 更新时是否会中断直播、聊天等正在进行的操作。
- 缓存是否可控、可清理、可排查。

综合评分：**55/100**。它已是可安装的在线 PWA，但断网白屏，尚不是可靠性成熟的 PWA。

## 我们要形成的差异

第一期只交付业务最需要、且风险可控的能力：

1. **安全离线壳与友好提示**：弱网时优先保证核心入口可打开；不缓存账号、支付、直播流、私有信息和写操作。
2. **受控更新**：避免在直播、表单等关键时刻强制刷新；支持可追踪的更新与紧急回退。
3. **上线前检查与真实浏览器验证**：安装信息、缓存边界、更新过程和登出清理都要在真实浏览器中验证，而不是只看代码。
4. **多业务复用**：不同前端业务通过统一方式接入，减少每个项目重新设计离线、缓存和发布规则的成本。

后续按价值追加，而不预先承诺：

| 后续能力 | 何时值得做 |
|---|---|
| 公共资讯/赛程的短期缓存 | 内容型业务有明确弱网访问需求时 |
| 系统通知 | 有明确召回场景、后端投递能力和频控方案时 |
| 受限离线提交 | 现场表单等必须断网工作的场景，且业务能处理重复与冲突时 |
| 域名迁移恢复入口 | 业务确有正式的多域名灾备、状态页和合规运维机制时 |

## 建议的投入与验收方式

采用“平台基线 + 一个试点业务”的方式推进，而不是先为所有业务一次性建设全部功能。

- **第一阶段目标**：一个业务完成可安装、弱网友好、更新受控、安全缓存和真实浏览器验收。
- **成功指标**：安装用户的回访率、弱网核心页可打开率、更新导致的中断率、缓存相关事故数。
- **不纳入第一期**：离线直播、任意数据离线缓存、无节制系统通知、自动跳转到其他域名和复杂离线提交。

## 需要管理层确认的事项

1. 是否同意以一个高频回访业务作为 PWA 试点。
2. 是否认可第一期优先级为“可靠与安全”，而非先做系统通知或大量离线功能。
3. 试点成功后，是否再按数据决定系统通知、公共数据缓存和域名灾备的投入。

接入评估需结合宿主项目的构建、部署和浏览器验证结果。
