# PWA 试点可行性与投入说明

> 本文是《PWA 决策简报》的附录，供需要评估试点投入、接入条件和责任边界的管理者阅读。

## 一、结论

建议采用“PWA 平台基线 + x9-web-pc 试点”的方式推进，但当前不宜把它承诺为即插即用的项目。

- **平台侧**：能力图与基础契约已经建立，当前处于真实浏览器验证基础设施阶段；可靠离线、更新控制、构建接入和 Vue facade 仍需按既定顺序完成，尚未形成可直接给 x9 安装的完整平台包。
- **x9 侧**：技术栈与第一期目标匹配（Vue 3、Vite、纯前端渲染），具备试点条件；但现有 PWA 尝试有明确的上线前阻断项，必须先处理。
- **管理建议**：现在可以批准“完成平台第一期并选择 x9 试点”的方向；具体上线日期与人力，应在 x9 的构建、部署和缓存边界完成核验后确认。

## 二、为什么选择 x9 作为试点

| 试点优势 | 已知约束 |
|---|---|
| Vue 3 + Vite，符合平台第一期支持范围 | 直播页面强依赖实时连接，不应承诺离线可看直播 |
| 已有 PWA 工具与 Worker 尝试，不是从零开始 | 本机构建曾失败，须先确认 CI 与生产构建是否可稳定通过 |
| 首页的页面框架、赛程、资讯适合弱网入口与离线提示 | 首页中的直播区、直播页、聊天室、登录、个人中心、上传和私有接口必须始终走网络 |
| 有构建版本标识与 CI/CD 基础 | 服务器响应头和 CDN 策略仍需运维确认 |

## 三、x9 接入前必须完成的条件

这些不是“体验优化”，而是决定是否可以安全上线的门槛。

| 优先级 | 必须确认或解决的事项 | 责任方 |
|---|---|---|
| P0 | 生产等价构建稳定通过；当前本地二次构建失败的问题有可重复、可修复的结论 | x9 前端团队 |
| P0 | 补齐应用安装信息和图标，明确用户可安装的产品身份 | x9 产品 + 前端团队 |
| P0 | Worker 版本与每次发布联动，避免新版本仍使用旧缓存 | 平台团队 + x9 前端团队 |
| P1 | 明确哪些页面和公共数据可离线：只允许页面框架与经批准、带时效标识的公共内容快照，且不含“直播中”、实时比分等实时状态；账号、支付、直播视频、私有数据和写操作一律不缓存 | 产品 + 平台团队 |
| P1 | 确认首页、Worker 与静态资源的服务器缓存规则 | 运维 + x9 前端团队 |
| P1 | 真实浏览器验证：安装、弱网/断网、更新、登出后的缓存清理；断网时首页不白屏，直播区不无限 loading，而是明确提示“需要网络” | 平台团队 + x9 前端团队 |

## 四、第一期交付边界

### 平台负责提供

- 统一的安装、离线提示、更新和缓存安全规则。
- 将首页拆为“可离线展示的页面框架与公共快照”和“必须联网的直播/实时区域”。
- 上线前检查与真实浏览器验证方法。
- 对 Vue/Vite 试点的接入方式和可审计报告。

### x9 仍需负责

- 选择哪些公共页面值得弱网支持，并提供离线文案。
- 修复自身构建、部署和业务接口问题。
- 保证登录、私有数据、直播流和写操作不被离线缓存。
- 为首页直播区提供离线状态文案；不得展示过期的“直播中”状态，也不得无限 loading。
- 和运维共同确认服务器响应头、CDN 与回滚流程。

### 第一阶段明确不做

- 离线观看直播或任意视频。
- 离线显示直播视频、实时比分、聊天室或“正在直播”等实时状态。
- 私有数据离线化、任意请求自动缓存。
- 系统通知的后端投递、离线提交和自动跳转到其他域名。

## 五、投入方式与验收

以三个可停止、可验收的阶段推进：

1. **上线准备**：完成 x9 P0 门槛核验。若构建或部署边界无法稳定，暂停上线，不把问题带入 PWA。
2. **试点接入**：平台完成第一期核心能力后，首页仅离线展示页面框架与经批准、带时效标识的公共快照，不包含“直播中”、实时比分等实时状态；赛程、资讯按时效展示缓存内容。首页直播区、直播页和私有页面始终联网，断网时明确提示“需要网络”。
3. **效果复盘**：以安装用户回访率、弱网核心页可打开率、更新中断率和缓存事故数决定是否扩大范围。

## 六、管理层下一步决策

1. 批准 x9 作为条件式试点，先完成 P0 上线准备。
2. 同意第一期按“可靠与安全优先”验收，不以 Push、离线直播等能力作为阶段目标。
3. 指定 x9 前端、产品和运维的责任人，完成 P0 核验后再审定具体排期与投入。
