# PWA 平台化与 x9 接入初步评估

> **历史快照（2026-09-15），不反映当前状态。** 文中的模块状态停留在评估当日：第 3 节列为"建设中"或"核心后续"的 browser-test-harness、workbox-engine、sw-runtime、client-runtime、build-verifier、vite-adapter 与 Vue facade 此后均已交付；Push、离线写入与 SSR 扩展也已实现并通过本地质量门禁（远端 CI 与真实设备证据仍未取得）。当前的决策口径以[《PWA 决策简报》](pwa-leadership-brief.md)及其附录[《PWA 试点可行性与投入说明》](pwa-pilot-feasibility-appendix.md)为准；本文保留外部案例、两条路径对比与第 9 节"排期前待确认事项"，供业务项目接入调研时参考。

> 读者：管理层、产品、前端、测试、运维
> 评估日期：2026-09-15
> 结论级别：初步评估。x9 的 CI、部署响应头和线上 Service Worker 历史尚待补充核验。

## 一句话结论

建议将 `pwa-platform` 建设为可复用的 PWA 基础能力，并让 x9 成为第一个 Vue/Vite 接入项目。x9 **当前尚未正式交付 PWA**，但其架构适合接入：项目接入基础复杂度为**中**，可靠上线复杂度为**中高**。首期只应交付安装、公共离线壳、公共资源缓存、受控更新和浏览器验收；不应把直播离线化、私有接口缓存、Push、离线写入或域名灾备混入首期。

这不是“给一个网站加安装图标”的项目。平台的长期价值是把缓存安全、版本更新、发布校验、浏览器验证和故障恢复从各项目的临时实现，转化为组织可复用的交付标准。

## 1. PWA 能解决什么问题

PWA（渐进式 Web 应用）让 Web 站点在符合条件的浏览器中拥有接近应用的入口和部分可靠性能力。它不是原生 App 的完全替代品。

| 能力 | 解决的问题 | 用户感受 | 首期建议 |
|---|---|---|---|
| 桌面安装 | 回访需要打开浏览器、输入网址 | 像 App 一样从桌面独立窗口打开 | 包含 |
| 离线应用壳 | 弱网或断网时直接白屏 | 能打开基础界面和网络提示 | 包含 |
| 公共资源缓存 | 重复打开慢、流量消耗高 | 已访问页面启动更快、更稳定 | 包含 |
| 公共内容短缓存 | 公共资讯在网络波动时不可访问 | 先看最近公共内容，再后台刷新 | 后续小步加入 |
| 受控更新 | 新旧资源混用、更新打断用户 | 在合适时机获得新版本 | 包含 |
| 系统通知 | 用户离开站点后难以召回 | 比赛、消息、活动提醒 | 后续模块 |
| 离线写操作 | 弱网时表单或任务操作丢失 | 联网后受控补发 | 后续模块 |

### 不应承诺的能力

- 离线观看任意直播、视频或实时比分；
- 所有页面、账号、订单、支付和私有消息永久离线；
- 通知必达或用户必然安装；
- 取代原生 App 的后台、硬件和应用商店能力；
- 跨域接管旧 PWA、复制旧 Cookie 或私有缓存。

## 2. 外部案例：`qwzb.live`

对公开页面、manifest 与 Service Worker 的观察显示，该站具备安装入口、iOS 基础适配、消息通知相关处理和 HTTPS 基础，但缺少可靠离线页面、完整缓存治理、受控更新与可观察的发布恢复闭环。

| 维度 | `qwzb.live` 的外部可见状态 | 结论 |
|---|---|---|
| 安装 | 有 manifest、图标、standalone 显示模式 | 已具备 |
| Push 基础 | 有 Push/通知点击处理 | 已具备基础 |
| 离线应用壳 | 未见页面与资源请求的可靠处理 | 明显不足 |
| 更新治理 | 立即激活，未见用户确认和回滚治理 | 风险较高 |
| 缓存安全与审计 | 未见策略验证与发布证据 | 不可证明 |

因此它证明“网站可以被安装”，但不证明“站点具有可靠的离线与更新能力”。此前基于公开可见信息的 PWA 能力评分约为 **46/100**：安装和通知较好，离线、更新、缓存治理较弱。

## 3. `pwa-platform` 的定位与当前状态

`pwa-platform` 不是让业务直接编写 Workbox 和 Service Worker 的工具集合。业务应用声明页面和资源的业务属性，平台据此执行缓存、更新、校验和验收。

```text
业务应用声明 PwaPolicy
        ↓
平台编译并执行安全 PWA 计划
        ↓
生成/校验 manifest、Worker、离线壳与构建产物
        ↓
浏览器验收、发布门禁、回滚与恢复
```

### 当前已交付与后续核心

| 模块 | 作用 | 当前状态 |
|---|---|---|
| contracts-foundation | 身份、策略、计划和生命周期契约 | 已完成 |
| policy-compiler | 将业务声明编译为安全 PWA 计划 | 已完成 |
| platform-governance | 浏览器矩阵、发布、回滚、恢复、供应链基线 | 已完成 |
| browser-test-harness | 真实浏览器 fixture 与 PWA 断言 | 建设中 |
| workbox-engine | 封装 Workbox，不向业务暴露原始配置 | 核心后续 |
| sw-runtime | 预缓存、离线壳、激活、清理与恢复 | 核心后续 |
| client-runtime | 安装引导、更新状态、登出清理 | 核心后续 |
| build-verifier | 身份、策略、产物和部署契约校验 | 核心后续 |
| vite-adapter、Vue facade | 对接 Vue/Vite 应用 | 核心后续 |

Push、离线写入、SSR、多 PWA 同源和域名迁移恢复属于后续扩展，不阻塞 x9 首期。

## 4. 有了完整核心包，哪些能力变得可控

| 维度 | 平台能控制什么 | 业务项目仍要决定什么 |
|---|---|---|
| PWA 身份 | manifest、scope、Worker URL、缓存命名空间的稳定性 | 产品名称、图标、主题色、启动页 |
| 缓存准入 | 默认拒绝私有数据、写操作、流媒体、Token 和未知请求 | 哪些页面/数据真实属于公共内容 |
| 离线体验 | 预缓存、离线壳、导航降级和资源清理 | 哪些页面可在离线时展示，文案如何表达数据时效 |
| 更新行为 | 等待更新、受控激活、缓存清理、恢复 worker | 直播、表单等敏感页面何时允许切换版本 |
| 构建交付 | manifest、Worker、scope、预缓存资源与策略一致性校验 | 使用的构建方式、产品资产和环境配置 |
| 浏览器质量 | 安装、离线、更新、登出等统一测试路径 | 业务关键流程和目标浏览器范围 |
| 发布治理 | 缓存响应头基线、回滚 Runbook、恢复演练要求 | CDN/Nginx 配置、发布窗口和运维执行 |

平台不能控制浏览器是否展示安装提示、用户是否授权通知、系统是否清理存储、网络/后端/DNS 是否可用，也不能把业务认证缺陷或实时业务变成离线能力。

## 5. x9 的初步接入评估

### 基线

x9 是 Vue 3 + Vite 5 的 CSR 项目，具有单一 HTML 入口、带指纹静态资源、公共浏览页面（首页、赛程、新闻）和既有 PWA/Workbox 实验资产。它不应被视为已经交付 PWA：本地审查中，历史 PWA 构建链路未能产生可验证的完整产物，且未发现产品化 manifest、完整图标和浏览器验收证据。

这不阻止新的平台化接入，但意味着旧 `sw.ts`、VitePWA 配置和缓存命名应视为**未验证实验资产**：可作为迁移参考，不能直接继承为生产方案。

### 评分

| 维度 | 初步判断 | 对接入的影响 |
|---|---|---|
| Vue/Vite/CSR 适配 | 有利 | 单入口应用壳和 Vite Adapter 的适配成本较低 |
| 公共页面离线范围 | 有利 | 首页、赛程、新闻适合首期 |
| 公共/私有 API 分类 | 需梳理 | 请求层混淆、接口未形成缓存分类文档 |
| 登录与本地状态 | 需严格约束 | Token/用户状态不能成为缓存准入依据或离线数据 |
| 直播、WebSocket、iframe | 需隔离 | 直播只在线，更新时机要受控 |
| 构建与发布 | 待验证 | 历史 PWA 构建、CI、响应头和回滚流程需确认 |
| 测试与浏览器验收 | 明显不足 | 当前缺少自动化与真实浏览器验证基础 |

**项目架构接入复杂度：中。**
**可靠上线复杂度：中高。**

上线复杂度高于架构接入复杂度的原因，不在 Vue/Vite 本身，而在测试、缓存发布治理、运维协作和实时业务更新策略。

## 6. 两条路径的取舍

| 维度 | x9 内部手写 PWA | 完成平台核心后接入 x9 |
|---|---|---|
| 首个演示版本 | 较快 | 较慢，需要等待核心 Runtime/Adapter |
| x9 业务侧接入成本 | 中 | 中低，以策略和验收为主 |
| 平台研发投入 | 无 | 高，需完成完整核心链路 |
| 缓存安全 | 项目自行审计 | 平台默认安全，业务补公共白名单 |
| 更新/回滚 | 项目自行维护 | 平台统一机制与治理要求 |
| 浏览器测试 | 从零建设或手工验证 | 复用 Harness 与 E2E 模板 |
| 第二、第三个项目 | 重新实现 | 低到中成本复用 |
| 长期维护风险 | 中高 | 低到中 |

### 推荐

如果只追求 x9 的一次性演示，手写可能更快；若目标是生产稳定性和后续多个项目复用，推荐完成平台核心后再接入 x9。不要同时维护一套 x9 特例 Workbox 方案和一套平台方案。

## 7. x9 首期范围

### 包含

- 安装能力：产品化 manifest、图标、独立启动体验；
- 公共离线应用壳：首页、赛程、新闻；
- 公共 JS/CSS/字体/经审核公共图片的缓存；
- 受控更新：普通页面提示刷新，直播等敏感页面延迟切换；
- 构建校验、浏览器验收、发布回滚与恢复预案。

### 不包含

- 直播间离线化、WebSocket/IM 缓存；
- 私有接口、个人中心、支付、上传、写操作缓存；
- Push 通知、离线写操作、SSR、多 PWA 同源；
- 域名迁移灾备。

## 8. 风险与发布门槛

| 风险 | 平台控制方式 | 仍需协作方 |
|---|---|---|
| 私有数据误缓存 | 默认拒绝，策略白名单和产物校验 | 业务确认 API 分类 |
| 新旧版本资源混用 | 等待更新、受控切换、缓存清理 | 产品定义敏感页面策略 |
| 发布错误 Worker | 恢复 worker、Runbook、演练 | 运维执行发布与回滚 |
| HTML/SW 长缓存 | 响应头基线与验证 | Nginx/CDN 配置 |
| 浏览器差异 | 浏览器矩阵与真实 E2E | 测试提供目标设备 |
| 存储配额与驱逐 | 缓存大小、数量、期限限制 | 产品确定离线范围 |

x9 首期上线前，必须同时具备：构建成功、完整 manifest、正常 Worker 注册、公共页面离线可打开、私有接口未被缓存、直播不被强制更新打断、正确响应头、浏览器验收通过，以及可执行的回滚/恢复方案。

## 9. 正式排期前仍需确认的事项

1. x9 CI/Docker 生产构建是否能稳定产生 PWA 产物；
2. 测试/生产环境对 HTML、`sw.js`、manifest 与带 hash 静态资源的缓存响应头；
3. 是否存在历史 Service Worker 的实际部署或用户端注册；
4. 前端域名、图片 CDN 和 API 域名的同源关系；
5. 产品确认的 manifest 名称、图标、主题色、首期公共页面；
6. 目标浏览器和 iOS 用户占比；
7. 团队是否接受首期以手工浏览器验收上线，或同步引入最小 E2E 覆盖。

## 10. 管理层建议

1. 将 `pwa-platform` 定位为组织级基础能力，而非 x9 的一次性插件。
2. 优先完成可接入的核心 Runtime、Adapter、Verifier 和 Browser Harness；不等待 Push、离线写入等扩展。
3. 让 x9 成为首个真实 Vue/Vite 接入样本，但只接入公共浏览能力。
4. 要求前端、测试、运维共同承担缓存策略、浏览器验收、响应头、发布回滚和恢复责任。
5. 在第 9 节事实补齐后，再给出正式人力和时间排期；当前只建议相对复杂度，不应承诺人天。

## 附：汇报时的准确表达

- 不说“x9 已经具备 PWA”，应说“x9 具备较好的 PWA 接入基础”。
- 不说“所有页面都能离线”，应说“首期保障公共浏览体验在弱网下更稳定”。
- 不说“PWA 可替代原生 App”，应说“PWA 改善 Web 的安装、回访和可靠性体验”。
- 不说“平台完成后零成本接入”，应说“平台把底层实现成本转化为项目侧的策略配置、产品资产和业务验收工作”。
