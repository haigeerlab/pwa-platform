# ADR-0034：离线导航兜底在精确匹配落空后忽略查询串

## 状态

已接受（2026-09-23）。修订 [ADR-0012](0012-platform-worker-runtime-config-and-recovery-worker.md) 所确立的平台 worker 导航行为中的兜底匹配规则，规格见 [spec/sw-runtime.md](../../spec/sw-runtime.md) 的"修订：导航兜底忽略查询串"。

## 背景

平台 worker 对导航请求网络优先；网络失败时按顺序尝试预缓存中的候选，都不中就返回网络错误。此前的候选是：**请求 URL 去掉片段、但保留查询串**；路径不以 `/` 结尾时再试同一 URL 加 `/index.html`（同样保留查询串）；最后是降级页。

这条"查询串必须一致"是当时的有意决定，写进了规格，并由 `decide.test.ts` 的用例连同注释钉住：带装饰参数的 URL 只会走到降级页。它的本意是不要把一个路由的缓存内容当成另一个路由的答案。

2026-09-23 在 Cloudflare 测试站的 `drill` 槽位做入口恢复演示时，这条规则造成了一个具体后果：应用按接入文档传入 `returnPath`，恢复页链接因此带上 `?return=…`。当前 Origin 在网络层不可达时，该导航的精确候选 `/app/pwa-entry.html?return=…` 与预缓存中的 `/app/pwa-entry.html` 匹配不上，于是跳过恢复页、落到离线降级页。**用户看到的是"您已离线"，而不是本该显示的备用入口列表**——恰恰是在这个功能唯一有用的时刻。

同一次断网下的对照实验：不带查询串访问恢复页正常显示入口按钮，带查询串则显示降级页。两次导航除查询串外完全相同。

## 决策

- **精确匹配仍然第一优先。** 请求 URL（去掉片段、保留查询串）命中预缓存时照旧返回它。
- **精确匹配落空后，再以同一 `pathname`（丢弃查询串）尝试一次**；随后是该 `pathname` 的 `index.html` 形式（同样丢弃查询串）；最后才是降级页。
- **"绝不返回其他路由的缓存内容"这条不变**：新增的候选只是同一路径去掉装饰参数，不会跨路由。
- 该规则只作用于**网络已经失败之后的兜底路径**。在线时网络响应原样返回，不受影响。

## 备选方案

- **维持原样，改由入口恢复模块把返回路径放进 URL 片段。** 不采用：它只挡住我们这次撞见的一例。任何业务把预缓存页面配上查询串访问，离线时仍会拿到降级页，而且没有任何提示，下一次以别的形式重现。
- **完全忽略查询串（连精确匹配一起）。** 不采用：预缓存中确实可能存在带查询串的条目，精确命中时应当优先返回它。
- **为导航请求引入查询串白名单。** 不采用：需要业务声明哪些参数"不影响内容"，把一个平台细节变成接入负担，收益不足。

## 影响

- **对查询串敏感的页面，离线时会拿到同路径的缓存文档**，而不是降级页。这是本决定的代价：与原先相比，用户拿到的是自己那一页的应用壳而非通用降级页，信息更多而非更少；页面在客户端仍可读取查询串自行渲染。**在线行为完全不变。**
- 入口恢复（`pwa-entry-resilience`）的恢复页在当前 Origin 不可达时可以正常打开，这正是该模块存在的前提。
- `decide.test.ts` 中钉住旧行为的用例及其注释随本决定改写；新增回归用例覆盖"带查询串 + 离线"。
- **演练缺口一并修补**：入口恢复演练第 4 步此前只验证应用壳能从缓存启动，没有在断网状态下真的打开恢复页，因此这个缺陷没有被演练发现。该步骤与驱动脚本同步补齐。
