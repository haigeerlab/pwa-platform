# ADR-0031：GitHub 不可用期间以本地干净门禁代替 CI 证据

## 状态

已接受（2026-09-22）。同日经独立评审后，由项目所有者收紧了替代条件、签署人与环境要求（见决策中"补充规则"）。临时决定：GitHub 仓库或 Actions 恢复可用时自动失效。修订[发布与事故处置手册](../operations/release-and-incident-runbook.md)中 CI 门禁项的证据形式，不改变基线 CI 本身（[spec/platform-governance.md](../../spec/platform-governance.md) 的"基线 CI"）。

## 背景

发布门禁要求"发布提交的 CI 运行已完成并通过"，证据是 CI 运行链接。项目的 GitHub 账号自 2026-09-18 起不可用，所有模块都只有本地测试结果，CI 证据一项始终为空，任何发布都无法通过门禁。

CI 的价值在于三点：环境干净、输入固定、结果可追溯。本地运行做不到"由第三方执行"，但可以在干净环境、固定输入和可追溯这三点上尽量接近。

## 决策

- **替代条件**：只在 GitHub 仓库或 Actions 不可用时适用。恢复可用后，此后的发布只接受真实 CI 运行链接。
- **执行方式**：每个 Node 版本各新建一个分离的 worktree，不复用任何已有目录、`node_modules` 或被 git 忽略的构建产物。在 Node 22 与 Node 24 下分别执行：`pnpm install --frozen-lockfile`、lint、build、test、typecheck，以及 Chrome 桌面端 N 的 `test:browser`；另外执行与 CI 相同的依赖审计（`pnpm audit --ignore-registry-errors`），审计结果不阻塞。每份日志开头先打印 `git rev-parse HEAD`、`node -v`、`pnpm -v`、UTC 时间与 Chrome 版本，使日志哈希能绑定到提交与运行环境。除审计外，每项退出码都必须为 0。
- **记录内容**：发布提交、Node / pnpm / 操作系统 / Chrome 的完整版本、执行的命令、每项退出码、每份日志的 SHA-256、开始与结束时间、执行者。格式见 `docs/operations/local-ci-record-template.md`。日志文件由发布系统保存，不提交到仓库，也不得包含令牌或私有数据。
- **补跑义务**：GitHub 恢复后，对每个以本地记录发布的提交补跑真实 CI，结果追加到对应的发布证据。补跑失败按事故处理。
- **发布证据中必须写明"CI 证据为本地替代（ADR-0031）"**，不得写成"CI 通过"。
- **补充规则**（项目所有者，2026-09-22 评审后）：
  - 发布提交只要已有任何 CI 运行结果（无论通过、失败或被取消），就不得使用本地替代。
  - 每次使用替代，都要记录当时的可用性检查：执行的命令、完整输出与 UTC 时间，例如 `gh auth status` 或 API 调用返回的错误原文。
  - 签署人必须是有名有姓的人类发布负责人。执行可以由他人或工具完成，签署人对记录负责。
  - 日志缺失、哈希不符，或保存期未满即被删除时，记录作废，必须重跑。日志至少保存到 GitHub 恢复后的补跑完成为止。

## 备选方案

- **等 GitHub 恢复。** 不采用：恢复时间不确定，门禁会无限期阻塞。
- **换一个 CI 平台。** 暂不采用：需要新账号和新的流水线配置，而基线 CI 是按 GitHub Actions 写的；恢复后还要维护两套。
- **直接豁免 CI 门禁。** 不采用：会失去干净环境与冻结依赖这两项保证。

## 影响

- **本地记录不能证明"由独立环境执行"。** 执行者本人可以篡改结果。日志哈希与干净 worktree 只能降低误差，不能排除故意造假；这一风险由发布负责人承担，并在发布证据中写明。
- **环境与 CI 不同**：基线 CI 在 ubuntu 上运行，本地替代通常在执行者的机器上运行（首次演练是 macOS）。平台相关的差异只能在补跑真实 CI 时发现。
- **执行成本上升**：每次发布要在两个 Node 版本下完整跑一遍，包括真实浏览器测试。
- **延长替代期限、放宽执行内容、或把本地记录当作永久方案，都需要新的 ADR。**
- 规格见 [spec/platform-governance.md](../../spec/platform-governance.md) 的"修订：桌面端发布通道与本地门禁替代 CI"。
