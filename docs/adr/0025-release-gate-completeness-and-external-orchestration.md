# ADR-0025：发布门禁完整性与外部发布编排

## 状态

已接受（2026-09-19）。"影响"末条中 Android 的阻塞范围已由 [ADR-0030](0030-desktop-release-channel.md) 按发布通道修订；CI 证据的形式由 [ADR-0031](0031-local-gate-substitute-for-ci.md) 临时补充（均为 2026-09-22）。项目所有者确认：门禁完整性使用独立类型化结果，不新增 `verify.*` 诊断码；网络、凭据、生产写入仍属于外部发布系统。

## 背景

`verifyRelease` 只执行调用方显式提供事实所对应的检查；输入省略时检查不出现，空报告的 `ok` 仍为 `true`。这是 [ADR-0014](0014-build-verification-boundary-and-report.md) 为保持纯函数边界作出的刻意选择，但发布方若只判断 `report.ok`，可能在没有身份基线、响应头或保留窗口证据时放行。

另一方面，响应头、线上资产、完整发布历史、基线更新和生产部署都需要网络、凭据与持久状态。把这些能力放进 Vite、Service Worker 或 build-verifier，会突破既有的零网络、零写入和最小权限边界。

## 决策

- `@pwa-platform/build-verifier` 新增纯函数的门禁完整性判定：调用方提供本次必须出现的检查名，函数只判断报告是否覆盖这些检查；它不重跑检查、不访问网络，也不把覆盖完整误称为全部通过。
- 正常发布必须同时满足：必需检查覆盖完整、`verifyRelease` 报告通过，以及运行手册规定的 CI、真实浏览器、安装和恢复演练证据齐全。
- 首次生产发布不得因缺少基线而自动通过。发布系统必须保留 `verify.baseline-missing` 的事实和平台负责人批准的首次发布记录；是否放行是发布系统的显式人工决定，不是 build-verifier 的推断。
- 发布系统或部署编排器拥有网络、部署凭据、每个 `appId` / `origin` / `environment` 发布线的完整记录和并发互斥。成功发布后才追加历史记录并更新 identity baseline；失败或撤销的候选不得伪装成成功发布。
- 本仓库只定义该外部协议和调用 build-verifier 的方式，不新增带凭据的 CLI、CDN 客户端或发布状态数据库。

## 备选方案

- **由 Vite 构建自动执行发布门禁。** 不采用：构建看不到线上响应、资产可用性、历史和人工证据。
- **让 build-verifier 请求 CDN 或写入发布记录。** 不采用：违反 ADR-0014 的纯函数边界，并引入凭据和非确定性。
- **只在运维文档中提醒调用方检查 `report.ok`。** 不采用：遗漏必需检查是可预见的错误，应有可测试的纯函数防线。
- **在本仓库实现通用部署 CLI。** 不采用：没有确定的托管平台或凭据模型；抽象会承诺尚未存在的集成面。

## 影响

- `build-verifier` 会增加一个小型公开纯函数及相应测试；不会改变已有 `verifyRelease` 的可选输入语义。
- 外部发布系统须按协议保存计划、时间、资产可用性和证据引用，并在每个部署槽位上串行执行。
- 浏览器矩阵的 Android N/N-1、桌面 N-1 和原生安装未取得时仍阻塞 V1 发布；不得以本地 Chrome N 结果替代。
