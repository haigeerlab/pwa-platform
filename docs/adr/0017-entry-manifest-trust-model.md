# ADR-0017：入口清单的信任模型

## 状态

已接受（2026-09-17，项目所有者）。服务 [pwa-entry-resilience](../../spec/pwa-entry-resilience.md)；交付边界见 [ADR-0018](0018-entry-resilience-delivery-boundary.md)。

## 背景

已安装的 PWA 绑定其原始 Origin。当这个 Origin 正在迁移或无法访问时，唯一能帮到用户的，是在旧应用里告诉他们新地址。**"告诉用户去哪里"本身就是一条钓鱼通道**：谁能改写这条信息，谁就能把一批已安装用户引到自己控制的域名。

而最需要这条信息的时刻，恰恰是旧 Origin 靠不住的时刻。它可能已经不可达，也可能已经不在我们手里。所以信息的可信度不能来自"它从哪里下载"，只能来自一个不依赖传输渠道的凭据。浏览器能用的只有 WebCrypto，不引入任何依赖。

## 决策

- **签名算法为 Ed25519，验签只用 WebCrypto。** 浏览器支持为 Chrome 137+、Firefox 129+、Safari 17+（MDN browser-compat-data），覆盖当前必测范围的 N 与 N-1。Node 24 的 `crypto.subtle` 是同一套 API，同一份校验代码在单元测试与浏览器中运行（已实测）。公钥为 32 字节原始格式，经 base64url 编码，以 `keyId` 标识。

- **先验签，后解析。** 签名覆盖 payload 解码后的原始字节。验签通过之前不调用 `JSON.parse`，也不做任何 JSON 规范化，因此不存在"两份等价 JSON、签名不同"的问题，未验签的内容也碰不到解析器。信封、清单、`reason` 与每个入口都是封闭形状，出现未知字段即拒绝。base64url 与时间戳按严格形态解析，拒绝填充、非规范尾比特与带毫秒或偏移的时间。

- **信任根是构建期的公钥集与种子清单。** 两者随应用构建发布，受版本控制。其余来源一律只是传输通道，不增加信任：
  - 发现源返回的清单必须验签；
  - IndexedDB 中的最后已知可信清单**每次使用都重新验签**，因为同源脚本可以改写它。

- **清单绑定到应用、环境与批准的 Origin。**
  - `appId` 与 `environment` 必须逐字相等，防止跨应用、跨环境重放。
  - 入口的 Origin 必须在构建期批准的列表中。**这把签名密钥泄露的后果限制在批准列表之内**：攻击者即使能签发清单，也只能把用户引到发布方事先批准的地址。
  - 运行时入口还不得等于当前页面的 `location.origin`。

- **新鲜度。** 清单带 `issuedAt` 与 `expiresAt`，允许 5 分钟时钟偏差；过期时间必须晚于签发时间；有效期不得超过构建配置的上限（默认 30 天，最大 90 天）。

- **防回滚。** `sequence` 单调递增，IndexedDB 记录保存写入时校验过的序号，作为下限：
  - 已存清单过期后，下限仍然有效，防止旧清单在新清单过期后被重放；
  - **下限只在已存清单的签名密钥仍在当前公钥集中、且未过 `notAfter` 时有效**（项目所有者 2026-09-17 决定）。落实方式是对已存信封**重新验签**（不检查过期），并核对签名内容中的应用、环境与序号与记录一致，这正是"每次使用都重新验签"的要求；实现最初只核对了 `keyId`，由模块质量门禁的独立评审发现并修正，决定本身不变。否则，泄露的密钥签发一份序号接近 `Number.MAX_SAFE_INTEGER` 的清单，就能让此后所有合法清单永远无法被接受，而从构建中移除该密钥也解除不了。放弃下限之后，回滚仍需要一份由现行密钥签发的旧清单，那是发布方认可过的内容。
  - 与下限持平或并列最大序号、payload 却不同的清单视为冲突，**失败即关闭**，不回退到较低序号。

- **密钥轮换与撤销都通过构建完成。** 轮换：发布同时含新旧公钥的构建 → 用新密钥签发 → 发布移除旧公钥的构建。撤销即发布移除该密钥的构建；`notAfter` 可为密钥预设失效时间。

- **私钥永不进入构建、仓库或浏览器。** 签名由发布流程离线完成。构建期拦截可识别形态的私钥：PEM 中的 `PRIVATE KEY` 字样、PKCS#8 DER 前缀 `302e020100300506032b657004220420`、64 字节的"种子加公钥"形态。测试密钥在测试运行时生成，仓库中没有任何密钥材料。

## 影响

- **有三类威胁本模块无法防御，如实登记：**
  - **旧域名被他人接管。** 接管者返回的任何 HTTP 响应都被平台 worker 当作网络可用，不会触发降级；接管者还能在旧 Origin 发布新的 worker。只能靠清单有效期上限与发布流程中的域名续费监控缩短暴露。
  - **签名密钥泄露。** 危害被批准 Origin 列表限制，但彻底处置需要发布新构建；已安装且长期离线的客户端在更新之前仍信任旧密钥。
  - **设备时钟严重偏差**会使过期判断失准。
- **32 字节原始私钥种子与公钥长度相同，按形态无法识别。** 误填进公钥配置时，只有当该密钥被用来校验种子、验签失败，构建才会失败。补偿措施写进发布与事故 Runbook 的密钥托管要求。
- **长期离线的安装会失去恢复能力。** 离线时间超过有效期上限后，种子与已存清单都会过期。上限越长，保住的离线安装越多，但被错误签发的清单也被接受得越久；30 天是在两者之间的取舍。
- **发布流程多出运维职责**：离线签名、序号递增纪律、双密钥过渡、撤回与撤销。这些写入 Runbook 的"入口清单签发、密钥轮换与撤回"一节。
- 实现见 `packages/entry-resilience` 的 `verify.ts`、`keys.ts`、`select.ts`；规格见 [spec/pwa-entry-resilience.md](../../spec/pwa-entry-resilience.md)。
