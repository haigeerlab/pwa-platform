# ADR-0038：显式开启的网络超时

## 状态

已接受（2026-09-24，项目所有者）。服务 [network-timeout](../../spec/network-timeout.md)。以增补方式修订 [ADR-0012](0012-platform-worker-runtime-config-and-recovery-worker.md)（导航判断）、[ADR-0013](0013-client-facade-and-page-side-lifecycle-events.md)（`served-from-cache` 的 `reason` 取值）与 [ADR-0035](0035-explicit-public-read-runtime-cache.md)（已知限制"不做网络超时"），见"对既有 ADR 的修订"。

## 背景

平台 worker 对导航与 network-first 运行时缓存都是"先等网络"：导航只有在请求被拒绝或返回错误响应时才使用离线回退，运行时缓存只有在网络失败时才用缓存。弱网下请求既不成功也不失败，只是挂着，用户会对着空白页一直等，直到浏览器自己放弃（通常以分钟计）。离线回退与运行时缓存明明已经就位，却用不上。

这影响所有配置了离线页的应用，包括 v1 中不开运行时缓存、只写了 `offlineFallback` 的业务。

## 决策

### 显式开启

- `PwaPolicy` v1、v2、v3 都新增可选字段 `networkTimeoutSeconds`（1–30 的整数）。不升策略版本：它是可选字段，旧策略原样有效。
- **默认关闭。** 未写时策略、计划与注入的 worker 配置与此前逐字节相同，请求判断不变；字段只在写了时出现，不以 `null` 或默认值占位。平台代码本身的变化见"影响"。
- 同一个值同时作用于导航与运行时缓存的 network-first。不提供按路由设置。

### 导航

设置了超时时，导航请求在 N 秒内没有收到响应头，就按与网络失败时相同的顺序使用回退（预缓存的应用壳或离线页）。

- 找到回退：立即返回。之后到达的网络结果被接住并丢弃，不写入任何缓存，也不产生未处理的拒绝。
- 一个回退都没有：继续等网络，之后按原有规则处理。**超时绝不把一个本来会成功的请求变成错误。**
- N 秒内网络有响应（包括 4xx、5xx）或失败：与此前相同。

导航超时由 sw-runtime 的 `navigate()` 自己实现，不经过 Workbox。

### 运行时缓存

network-first 的运行时缓存把超时交给 Workbox `NetworkFirst` 的 `networkTimeoutSeconds`。2026-09-24 核对 Workbox 7.4.1 源码：超时时缓存命中则用缓存；未命中则继续等网络；网络响应晚到时通常会写入；worker 被回收时可能丢失（尽力而为）——晚到的写入经由 `StrategyHandler.waitUntil` 而非直接延长 `FetchEvent` 的生命周期（`StrategyHandler.js` 的 `waitUntil`、`doneWaiting` 与构造函数），一旦 worker 在这之前被终止，写入就会丢失。stale-while-revalidate 不受影响。

### 页面事件

`served-from-cache` 的 `metadata.reason` 新增 `network-timeout`：超时后由缓存应答时使用。网络在超时前失败、由缓存应答时仍为 `network-failed`。页面据此可以区分"网络太慢"与"网络断了"。

## 对既有 ADR 的修订

- **ADR-0012**：导航判断在"网络响应或网络失败"之外，增加"设置了超时且 N 秒内无响应"这一种使用回退的条件；回退列表与顺序不变。
- **ADR-0013**：`served-from-cache` 的 `reason` 取值由两个增为三个。这是事件契约的扩展，按 `reason` 分支处理的业务需要接住新值。
- **ADR-0035**：已知限制"不做网络超时"解除；其余已知限制不变。

## 影响

- 平台 worker、恢复 worker 与页面脚本都会略有变化，所有应用都承担，包括未开启的应用：导航的计时器分支在平台 worker 中，页面侧对 `reason` 的校验与 worker 共用同一份代码（2026-09-24 NT4 实测，vite 夹具中这三类文件的字节改变）。未开启时注入的 worker 配置不含新键、与此前逐字相同，其余构建产物逐字节相同。
- 超时后网络请求并不中止，照常完成；导航路径丢弃其结果，运行时缓存路径通常会写入；worker 被回收时可能丢失（尽力而为）。弱网下因此仍会消耗流量。
- 业务对"多少秒算慢"需要自己取舍：取值太小，网络稍慢时用户就会看到离线页或旧数据。接入说明给出建议值。

## 拒绝的方案

- **默认开启**：会悄悄改变所有已上线应用在弱网下的行为，与平台"显式开启"的做法不一致。
- **只放在 v3 的 `runtimeCache` 里**：v1 业务的导航用不上，而那正是最常见的场景。
- **超时后中止网络请求**：可以省流量，但会让运行时缓存无法用晚到的响应更新，也可能中止一个即将成功的请求。
- **复用 `network-failed` 作为超时的 `reason`**：页面无法区分网络慢与网络断，而两者对用户的提示不同。
