# 关卡 5：发布门禁（可选）

进入条件：关卡 4 通过，且业务方有自己的发布系统或 CI。目的：说明怎样用 `build-verifier` 把发布前的机器检查接进去。**v1 只给指引，不代为采集**响应头、基线或历史资源，也不替业务方部署。

## 原则

- 规则的来源是 `build-verifier`（`verifyRelease()`）与《部署与发布》，本文件不另立规则。
- 你不请求线上地址来替业务方填 `observed`：采集是他们发布流程的事，关卡 3 的 curl 只是接入期的人工核对。
- 业务方可以**明确放弃**本关卡。放弃要写进状态文件（谁、何时、原因），不能默默略过。

## 所需输入

`verifyRelease()` 只运行**给了输入**的检查。**省略某个输入，就跳过对应检查，报告里不出现它**，所以 `ok: true` 不等于全部检查通过。要求业务方逐项给出，或明确说明省略哪项、为什么：

| 检查 | 输入 | 从哪来 |
| --- | --- | --- |
| `artifacts` | `plan` 与 `published`（构建实际发布的绝对路径） | 构建产物清单 |
| `response-headers` | `observed`：线上 worker、manifest、指纹资源的响应头，按路径 | 发布流程对线上 URL 的采集，对应关卡 3 的 S1、S2、S4 |
| `html-headers` | `htmlObserved`：公开 HTML 的响应头，按路径，跟随同源重定向后取最终响应 | 同上，对应 S3 |
| `identity-baseline` | `baseline`：该环境已登记的身份基线；查过但没有要传 `undefined`，不是省略 | 身份发布基线记录 |
| `release-order` | `deployedRootPlan`：同域根应用当前线上的计划（仅共享 origin 的子应用） | 根应用的发布记录 |
| `release-retention` | `retention`：旧指纹资源当前是否可获取与历史发布记录 | 发布系统，对应 S8 |

## 怎么给指引

1. 问业务方发布系统是什么，哪些输入它已经有。
2. 对缺的输入逐项说明它对应哪条服务端要求，问是补上还是明确不做。
3. 把结论写进状态文件："已接入 / 部分接入（缺哪些）/ 明确放弃"。被省略的检查一律不算通过。

## 通过标准

业务方确认已接入，或明确放弃并留下记录。

## 闸门

生产部署与 worker 切换由人执行（G5）。你只询问结果并把人的陈述记进状态文件，不推送、不部署、不切换。
