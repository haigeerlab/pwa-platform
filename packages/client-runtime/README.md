# @pwa-platform/client-runtime

Browser-side lifecycle facade for PWA Platform. It owns service-worker registration, install prompting, explicit
update confirmation, update checks, logout cleanup and typed lifecycle events. Vue and React applications should
normally use `@pwa-platform/vue` or `@pwa-platform/react`; use this package directly for another framework or a
framework-free application.

Requires Node.js 22 or later for installation/build tooling. The main entry is browser-only.

## Install

```sh
npm install @pwa-platform/client-runtime
```

The client config is normally generated by `@pwa-platform/vite`:

```ts
import config from "virtual:pwa-config";
import { createPwaClient } from "@pwa-platform/client-runtime";

const client = createPwaClient({
  config,
  // Optional. Checks only while the page is visible; omitted means disabled.
  updateCheck: { intervalMs: 30 * 60_000 },
});

const unsubscribe = client.subscribe((event) => {
  if (event.type === "update-waiting") showUpdateButton();
  if (event.type === "install-eligible") showInstallButton();
});

await client.register();

// On an explicit user action:
await client.promptInstall();

// After the user confirms an update:
if (await client.applyUpdate()) location.reload();

// When the application is torn down:
unsubscribe();
client.dispose();
```

Call `register()` only in the browser, normally only for a production build. `vite dev` exposes the virtual config
but does not emit the production worker or precache.

## Public API

| API | Purpose |
| --- | --- |
| `createPwaClient(options)` | Validates the config and creates one lifecycle facade. |
| `register()` | Registers the configured worker and starts observing install and update state. Repeated calls reuse the first registration. |
| `promptInstall()` | Shows a saved browser install prompt; returns `accepted`, `dismissed` or `unavailable`. |
| `checkForUpdate()` | Calls `registration.update()` now; returns `update-available`, `up-to-date` or `unavailable`. |
| `applyUpdate()` | Confirms a waiting worker, waits for takeover and returns whether an update was applied. It never reloads the page. |
| `logout()` | Clears the worker-owned offline-write queue, then unregisters; returns `false` if cleanup cannot complete. |
| `subscribe(listener)` | Observes lifecycle envelopes and returns an unsubscribe function. |
| `dispose()` | Removes listeners, timers and pending waits. Later method calls reject. |
| `validateClientConfig(value)` | Validates a page-side config independently. |

`CLIENT_EVENT_TYPES` contains `registered`, `install-eligible`, `installed`, `update-waiting`, `update-applied` and
`served-from-cache`. Event metadata is deliberately flat and non-sensitive: do not add tokens, user identifiers,
response bodies or private endpoint data in downstream telemetry.

The optional `updateCheck.intervalMs` is a visibility-aware page timer. It is not the browser Periodic Background
Sync API, and it does not activate a new worker without user confirmation. The first installation can make
`checkForUpdate()` return `update-available`; show update UI from the later `update-waiting` event, not from that
return value alone.

## Build-time entry

`@pwa-platform/client-runtime/build` exports `createClientConfig()` and `validateClientConfig()` for build adapters.
Application code normally should not import this entry.

## Security and lifecycle boundaries

- The config fixes the application id, scope and exact worker URL; the facade does not discover or widen them.
- `applyUpdate()` is confirmation-only. The application owns the prompt, unsaved-work handling and final reload.
- `logout()` is the supported cleanup sequence for session-bound queued writes. Treat a `false` result as incomplete
  cleanup and do not silently claim that local PWA state was removed.
- A facade is browser state, not an SSR service. Create or call it only after hydration.
