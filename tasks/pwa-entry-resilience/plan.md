# Plan: pwa-entry-resilience

> 标题按 spec-guard Proposal 晋升校验要求以 `# Plan:` 开头。规格：[spec/pwa-entry-resilience.md](../../spec/pwa-entry-resilience.md)。

## 概览

交付新私有包 `@pwa-platform/entry-resilience`：签名入口清单的契约与校验、页面侧查询函数、平台入口恢复页、Vite 插件，以及真实浏览器证据；另对已交付的 `@pwa-platform/vite` 做一处增量修改（只读计划 API）。

本模块的风险不在代码量，而在四处：

1. **信任判断写错一处就是钓鱼通道。** 签名、序号、过期、批准 Origin、返回路径，每条拒绝规则都必须有能失败的测试。
2. **"多个 Origin"在测试里怎么造。** 批准的 Origin 必须在构建时写定，而 fixture 服务器端口由系统分配；这个前提不先打通，后面的真实浏览器证据都无从谈起。
3. **改动已交付包。** vite-adapter 的计划 API 是公开契约的增量，必须不改变既有行为，并修订 ADR-0015。
4. **落地形态受晋升校验约束。** 见"落地方式"。

## 架构决定

- **纯逻辑与浏览器外壳分离。** 清单校验、选择规则、返回路径校验都是纯函数，通过注入的端口（时钟、存储、网络）工作，在 Node 中完整单测；浏览器侧只剩 IndexedDB、`fetch` 与 DOM 的薄适配。沿用 react 绑定 `store.ts` 的做法：能在单测里覆盖的，不留给 E2E。
- **验签只用 WebCrypto。** Node 24 的 `crypto.subtle` 与浏览器是同一套 API，同一份校验代码在单测和浏览器里跑。
- **先打通多 Origin 的浏览器前提，再建界面。** T2 是一个带结论的探路任务：结论决定 E2E 的站点构建方式，而不是边写边改。
- **vite-adapter 的改动独立成任务并优先 TDD。** 它不依赖本包其他任务，可与 T1–T3 并行。
- **ADR 在决定落到代码之前写。** ADR-0015 修订随 T4 一起；ADR-0017、ADR-0018 在 T5 开工前完成，因为插件与页面的实现直接执行它们。

### 已实测确认的前提（2026-09-17）

- **Node 24.18.0 的 WebCrypto 能验 Ed25519。** `node:crypto` 生成密钥对，从 SPKI DER 取末 32 字节作为原始公钥，`crypto.subtle.importKey("raw", …, { name: "Ed25519" })` 后验签 64 字节签名返回真。
- **Ed25519 私钥的 PKCS#8 DER 为 48 字节，前缀 `302e020100300506032b657004220420`**，与规格中构建期拦截规则一致。
- **浏览器支持**：WebCrypto Ed25519 验签在 Chrome 137+、Firefox 129+、Safari 17+（MDN browser-compat-data），当前 Chrome 152 覆盖 N 与 N-1。
- **harness 提供的 `fixtureServer` 不能在测试中途关闭**：测试结束时 harness 会再次 `close()`，而 Node 对已关闭的服务器会回调错误，teardown 因此失败。需要"中途不可达"的 Origin 必须由测试自己用 `startFixtureServer` 启动并关闭。
- **`startFixtureServer` 不接受端口参数**，端口由系统分配。批准的 Origin 必须在构建时写定，这是 T2 要解决的问题。
- **平台 worker 的导航策略**：网络有任何响应就用网络（含 4xx/5xx），网络层失败才回退到同路由的预缓存页，再到离线页（`packages/sw-runtime/src/worker/decide.ts`）。

## 任务定义

### 任务 1：包骨架、清单契约与验签

**说明：** 建立 `packages/entry-resilience`，实现签名信封与清单的解析、Ed25519 验签、公钥集校验。只有纯函数，不含浏览器代码。

**验收标准：**

- `package.json`：私有、`type: module`，脚本 `build`、`test`、`typecheck`（`test:browser` 随 T2 加入）；不新增第三方依赖。
- `tsconfig` 的 `include` 覆盖全部源文件扩展名；显式声明 `@types/node`（lockfile 已有 24.13.4），不依赖仓库之外可解析到的类型。
- 先验签、后解析：验签对象为 `payload` 解码后的原始字节。
- 规格"契约"一节中的每条拒绝规则各有至少一个单元测试：无效签名、篡改 payload、未知 `keyId`、`notAfter` 已过、公钥格式错误、未知字段、`schemaVersion` 不符、`appId` 或 `environment` 不符、过期、`issuedAt` 超前超过 5 分钟、有效期超上限、`status`/`reason` 取值非法、`message` 超长或含控制字符、`entries` 超过 5 条、非规范化 Origin、非 HTTPS 且非本地地址、未批准 Origin、`startPath` 非法。
- 测试密钥对在测试内由 `node:crypto` 生成；仓库中不出现任何私钥，包括测试用的。
- 诊断只含码与契约路径，不回显输入值。

**验证：**

- `pnpm test --filter @pwa-platform/entry-resilience`、`typecheck`、`build` 通过。
- 变异检查：注释掉"先验签后解析"中的验签调用，签名相关用例必须转红；把批准 Origin 检查改为恒真，未批准 Origin 用例必须转红。

**依赖：** 无。

**预计范围：** M（包配置、契约类型、校验、测试）。

#### T1 实施记录（2026-09-17）

**实现由 `executor` 子代理完成，主会话验收。** 交付 `packages/entry-resilience`：严格 base64url 解码（不用 `atob`/`Buffer`，拒绝填充与非规范尾比特）、严格时间解析（不用 `Date.parse`）、Origin 规范化、封闭形状校验、`validateKeys` 与 `verifyEnvelope`。本包零运行时依赖，`src/` 不导入任何 `node:` 模块，由按文件的导入守卫测试钉死。lockfile 只多出本包的 importer 段（`@types/node@24.13.4` 已在 lockfile 中）。

**验收中主会话补了两处。**
- **过期早于签发未被拒绝。** `issuedAt` 落在 5 分钟容差内、`expiresAt` 仍在未来时，一份"签发在过期之后"的清单原本会被接受。新增 `entry.validity-period-invalid`。原"已过期"用例的夹具恰好是零长度有效期，改为签发早一天，使该用例只测过期一条规则。
- **解码前的长度上限。** 64 KiB 上限原本在解码之后才检查，超长字符串会被完整遍历；新增按 base64url 长度的前置检查。

**实施中澄清的规格细则**（已写回规格"契约"一节）：
- 时间严格为 `YYYY-MM-DDTHH:mm:ssZ`；
- 嵌套对象同样封闭形状；
- 过期必须晚于签发。

子代理提出的另两点按其实现接受：信封级失败的诊断路径为空串；T1 不依赖 contracts，T5 接入真实身份时再评估。

**变异检查**（每次还原后与变异前逐字节一致，基线复跑全绿）：

| 变异 | 结果 |
|---|---|
| 验签调用改为恒真（子代理做一次，主会话复做一次） | 恰好两条签名用例转红 |
| 批准 Origin 检查改为恒真（子代理） | 恰好一条未批准 Origin 用例转红 |
| 删除"过期须晚于签发"规则 | 恰好新增用例转红 |
| 删除解码前长度检查 | 恰好新增用例转红（该用例用非法字符构造，缺少前置检查时会报编码错误而非超长） |
| 在 `src/index.ts` 注入 `import "node:fs"` | 导入守卫用例转红 |

**给 T6 的记录。** `startPath` 的规则没有覆盖百分号编码形态，这与规格一致：它拼接在固定 Origin 之后，而 URL 的 authority 在第一个 `/` 处结束，路径部分无法改变 Origin。恢复页实现时仍须用 `new URL(startPath, origin)` 构造并断言结果的 `origin` 等于批准的 Origin，作为纵深防御。

**过程中的异常。** 子代理报告 `spec/CAPABILITY-MAP.md` 末尾出现两行终端界面残留文字（来源不明，不是本任务写入），它**自行用 `git checkout` 还原了该文件**。主会话核实文件现与 HEAD 一致。被还原的内容已无法找回；这次还原超出了子代理的任务范围，本应先停下来报告。

**结果**：65 条单元测试通过；本包 typecheck、build 与全仓 lint 退出 0；私钥扫描（`PRIVATE KEY` 字样、PKCS#8 前缀）无匹配。

### 任务 2：多 Origin 真实浏览器前提（探路）

**说明：** 在真实 Chrome 中打通本模块 E2E 需要的全部前提，给出书面结论后再进入界面实现。

**验收标准（每项给出实测结论，写入实施记录）：**

- **站点构建与端口**：找到一种不修改 browser-test-harness 的方式，让构建时写定的批准 Origin 与发现源地址等于测试中实际启动的服务器 Origin。候选做法：
  - 先用空目录启动服务器，拿到端口后再构建到该目录（前提是服务器在请求时读盘，需实测）；
  - 在 `global-setup` 中启动服务器、构建，并通过环境变量把地址交给测试（测试间隔离性变弱，需说明）。

  两者都不成立时停下来询问，不擅自修改 harness。
- **主 Origin 不可达**：由测试启动、再关闭的服务器，在关闭后平台 worker 能从预缓存启动应用壳，页面内对主 Origin 的探测表现为网络错误。
- **备用 Origin 可达**：`no-cors`、`credentials: "omit"` 的跨 Origin 探测在备用服务器存活时成功、关闭后失败。
- **发现源跨 Origin 读取**：fixture 服务器通过 `headerRules` 返回 CORS 头后，页面能读取清单内容；不返回时读取失败。
- **浏览器验签**：T1 的校验代码在 Chrome 中对 Node 生成的签名验签成功，对篡改的签名失败。
- **IndexedDB 与恢复 worker 共存**：部署 ADR-0005 的恢复 worker 后，本模块的 IndexedDB 库仍在。

**验证：**

- `packages/entry-resilience/browser-tests/feasibility.spec.ts` 覆盖上述每项且通过；每项的断言各做一次反向检查（例如不返回 CORS 头时读取必须失败），证明断言不是恒真。
- 探路测试在 T7 中被正式场景取代或保留为前提回归，二者择一并在 T7 记录。

**依赖：** 任务 1。

**预计范围：** M。

#### T2 实施记录（2026-09-17）

**结论：六项前提全部成立，均不需要修改 browser-test-harness。** 证据在 `browser-tests/feasibility.spec.ts`，六条测试各自带反向检查。

| 前提 | 结论 | 反向检查或变异 |
|---|---|---|
| 站点构建与端口 | **采用候选方案一**：先用空目录启动三台服务器，再构建到主 Origin 的目录，把真实 Origin 写进构建。成立的依据是 `startFixtureServer` 启动时只解析根目录，文件在每次请求时才读盘（`server.ts` 的 `handle`） | 三台服务器的 Origin 互不相同，排除"三个名字指向同一台" |
| 主 Origin 不可达 | 由测试自己启动并关闭的服务器，关闭后重载，平台 worker 从预缓存启动应用壳；同 Origin 探测在网络层失败 | 关闭前探测成功（返回 404）；**变异 M1**：关闭前先注销 worker，重载即 `net::ERR_CONNECTION_REFUSED` |
| 备用 Origin 探测 | `no-cors`、`credentials: "omit"` 的跨 Origin 请求，服务器在时成功、关闭后失败 | 同一测试内先成功后失败 |
| 发现源跨 Origin 读取 | 发现源返回 `access-control-allow-origin` 后可读；请求是简单 GET，不触发预检（fixture 服务器只接受 GET 与 HEAD，因此这一点很重要） | 先断言无 CORS 头时读取失败 |
| 浏览器验签 | T1 的 `verifyEnvelope` 在 Chrome 152 中验过 `node:crypto` 生成的签名，篡改一个字节即以 `entry.invalid-signature` 拒绝 | 篡改用例本身 |
| IndexedDB 与恢复 worker 共存 | 部署 ADR-0005 的恢复 worker 后，应用前缀下的缓存全部删除，而 IndexedDB 库原样保留 | 前置断言应用确有缓存可删；**变异 M2**：让恢复 worker 顺带删除该库，断言以 `Received: null` 转红 |

**选定方案的代价。** 每条测试都要自己构建一次站点（本机约 0.4–0.9 秒一条），且不能使用 harness 提供的 `fixtureServer`：测试结束时它会再关一次服务器，对已关闭的服务器 Node 会回调错误。`browser-tests/sites.ts` 的 `close()` 保证每台服务器只关一次。构建产物写在系统临时目录，`afterEach` 清理；重复运行 60 次后无残留目录。

**过程中修掉的两个问题。**
- **异步谓词会让等待空过。** `waitForActivatedWorker` 最初写成对 `page.waitForFunction` 传异步谓词。Playwright 不等待这种谓词，返回的 Promise 为真值，首轮轮询即通过——`packages/vite/browser-tests/update.spec.ts` 曾记录同一问题。改为页面内轮询。
- **M2 起初以超时失败，没有死在断言上。** 数据库被删后再打开会得到一个新建的空库，读取不存在的对象仓库会在成功回调里同步抛错，Promise 永不结束。读取改为"库或仓库不存在即返回 null"后，M2 变为 3.4 秒内以断言失败。

**稳定性**：整份文件 `--repeat-each 10`，60/60 通过。

**依赖**：新增的 devDependencies（`@playwright/test@1.63.0`、`vite@8.3.0`，以及 browser-test-harness、contracts、vite 三个工作区包）在 lockfile 中均已有相同版本，没有新的外部包。

**类型检查覆盖**：新增 `tsconfig.browser.json`（Node 侧测试与站点构建）与 `tsconfig.app.json`（fixture 页面，`types` 为空、带 DOM lib）；`--listFilesOnly` 确认所有新文件都在程序中，`@types/node` 解析到仓库内的 24.13.4。

**给 T7 的决定**：`feasibility.spec.ts` 保留为前提回归，T7 的正式场景复用 `sites.ts`。**计划要求在进入 T5 之前，由项目所有者复核本结论。**

### 任务 3：选择规则、返回路径与页面侧查询函数

**说明：** 实现清单来源选择、IndexedDB 存储适配、主入口与备用入口探测、返回路径校验，以及 `checkEntryRecovery()`。

**验收标准：**

- 选择规则为纯函数，通过注入的时钟、存储、网络端口工作：取合法候选中序号最大者；同最大序号而字节不同时结果为"无入口"并记录 `entry.sequence-conflict`；发现源清单序号严格大于已存序号时才写入。
- 存储读出的信封每次重新完整校验。
- 返回路径校验通过规格列出的全部绕过用例：`//evil`、`/\evil`、`/%2F%2Fevil`、`/%5Cevil`、`/a/%2E%2E/b`、控制字符、scope 外路径、超长；合法路径原样保留。
- 状态与展示规则：`migrating`、`incident` 展示；`normal` 仅在主入口探测失败且至少一个备用入口探测成功时展示为 `unconfirmed-outage`；两者都失败（设备离线）时不展示。
- `checkEntryRecovery()` 从不抛出；结果中不含备用入口地址；`recoveryPageUrl` 只带经校验的返回路径。
- 发现源请求：`credentials: "omit"`、`redirect: "error"`、`cache: "no-store"`、5 秒超时、64 KiB 上限，均有单元测试（经注入的网络端口）。

**验证：**

- 单元测试通过；以上每条规则各一次变异（例如去掉同序号冲突判断、把返回路径的解码后复查去掉），对应用例必须转红。

**依赖：** 任务 1。

**预计范围：** L（选择、存储、探测、返回路径、查询函数）。若实施中超过 5 个源文件，拆出"返回路径校验"为独立提交。

#### T3 实施记录（2026-09-17）

**实现由 `executor` 子代理完成，主会话按预先定死的接口验收。** 交付：
- `return-path.ts`，单独提交为 `24fc00a`，隔离状态下 82 条用例通过；
- `select.ts`（选择规则）、`decide.ts`（展示判定）、`check.ts`（编排与 `runEntryRecovery`，从不抛出）；
- `src/browser/` 下的发现源请求、探测、IndexedDB 存储与 `createEntryRecoveryChecker`。

浏览器适配层用注入的假 `fetch` 单测：请求选项逐项断言，响应体按实际收到的字节计数，不信任 `Content-Length`。**`indexeddb.ts` 没有单元测试**（Node 无 IndexedDB），由 T7 的真实浏览器测试覆盖；它与 T2 探路测试验证过的读写形态一致。

**子代理发现的一个现象。** 去掉返回路径"解码后复查"这条规则时，原有用例一条都没转红：URL 解析器会把 `%2E%2E` 规范化掉，而 `%2F`、`%5C` 按字面保留，攻击串的 pathname 因此都落在 scope 之外，被 scope 检查拦下，掩盖了这条规则失效。子代理加了一条 scope 为 `/` 的隔离用例，变异后该用例转红。

**验收中主会话修了三处。**
- **`currentOrigin` 失败时回退成空串**，会悄悄让"入口不得指向当前 Origin"失效。改为 `currentOrigin` 或时钟任一不可用时失败即关闭（`entry.runtime-unavailable`），并挪到任何存储与网络访问之前；用例断言此时既不读存储、也不请求发现源。
- **写入失败复用了读取失败的码**，改为 `entry.storage-write-failed`。子代理自己提出了这一点。
- **IndexedDB 写入没有处理事务中止**：配额耗尽时 Promise 会挂起，已补 `onabort`。

子代理提出的其余几点按其实现接受：
- 选择诊断的路径带来源前缀（`/seed`、`/stored`、`/discovery`），不回显任何值；
- `normalizeReturnPath` 不进入公开导出，包内使用；
- 浏览器工厂的配置在 `EntryRuntimeConfig` 上补了 `mountPath`，T5 接入虚拟模块时再定形。

**过程中两次无效的变异运行，如实记录。** 一次补丁脚本在改用例时因锚点匹配到两处而中止，源码已改、用例未改；另一次新用例尚未通过。这两次的"变异转红"都发生在基线本就失败的状态下，**不计入结论**。以下变异均在全绿基线上完成，还原后 `shasum` 一致：

| 变异 | 转红用例 | 执行者 |
|---|---|---|
| 去掉最大序号冲突判断 | 两个候选同序号不同 payload → `none` | 子代理；主会话复做一次 |
| 去掉序号下限 | 三条下限相关用例 | 子代理 |
| `recordToStore` 严格大于改为大于等于 | 与下限持平时不写入 | 子代理 |

**结果**：128 条单元测试通过；本包 typecheck、build 与全仓 lint 退出 0。

**待项目所有者决定：签名密钥撤销与序号下限的冲突。** 按现行规则，已存清单的序号下限在清单失效后依然有效。设想签名私钥泄露：攻击者签发一份序号极大（例如接近 `Number.MAX_SAFE_INTEGER`）的清单并被用户设备存下。此后即使发布移除该密钥的构建，下限也不会消失，任何合法清单都再也无法被接受，直到用户清除站点数据。可选做法：
- **只有已存清单的签名密钥仍在当前公钥集中（且未过 `notAfter`）时，才采用它的序号下限**；密钥被撤销即放弃下限。回滚攻击仍需要一份由现行密钥签发的旧清单，而现行密钥签发的内容本就是发布方认可的；
- 维持现状，把"序号不得跳跃过大"写进 Runbook，靠发布流程约束；
- 给序号设置上限，并规定单次递增的最大步长。

这一决定会改动 `select.ts` 与规格，需要在 T7 之前定。

**决定与落实（2026-09-17）**：项目所有者选择第一种做法。`sequenceLowerBound` 现在只在已存信封的 `keyId` 仍在当前公钥集中、且未过 `notAfter` 时采用下限。原用例"已存信封不再合法时下限依然有效"恰好用了未知密钥，按新规则正是应当放弃下限的情形，因此改为"由现行密钥签发、只是已过期"。另补两条放弃下限的用例：密钥已从公钥集中移除（以接近 `Number.MAX_SAFE_INTEGER` 的序号模拟泄露密钥钉死下限）、密钥已过 `notAfter`。

三次变异在全绿基线上执行，还原后一致：去掉密钥存在检查 → 撤销用例转红；去掉 `notAfter` 检查 → 过期密钥用例转红；下限整体失效 → 三条下限相关用例转红。130 条单元测试通过。

- **设备离线**：结果为 `none`；恢复页显示"当前没有可用的备用入口"，页面上没有按钮。
- **撤回**：更高序号的 `normal` 清单撤回迁移公告；重放旧信封不被接受，存储保持序号 3，信封逐字未变。
- **篡改**：全新设备上，篡改信封与未知密钥签发的清单都不展示、不写入存储；已存有合法清单时，篡改的高序号信封不覆盖存储，结果继续来自已存清单。规格原来的"不展示入口"一句据此拆分为两种情形。
- **恢复 worker 共存**：应用缓存被删除（证明恢复 worker 确实运行过），IndexedDB 记录保留；发现源不可读时，仅凭已存清单仍返回 `migrating`。

**子代理报告的一处返工：篡改用例原本没有测到验签。** 最初沿用 T2 的做法翻转 payload 倒数第 3 个字节，恰好落在 JSON 的 `}` 上。即使把验签改为恒真，`JSON.parse` 也会先失败，测试照样通过，签名这道防线根本没被测到。改为在清单固定的纯 ASCII 文本字段内部翻转一个字节，篡改后 JSON 与各字段依旧合法，拒绝只能来自签名不匹配。

**变异检查**（全绿基线，还原后一致）：

| 场景 | 变异 | 转红位置 | 执行者 |
|---|---|---|---|
| 计划迁移 | 只有一个入口时自动导航 | 等待按钮出现时超时：页面已被导航离开 | 子代理 |
| 网络层不可达 | `normal` 一律判为 none | 结果不是 `available` | 子代理 |
| 设备离线 | 主入口失败时不再要求备用入口可达 | 离线结果变为 `available` | 子代理 |
| 撤回 | 去掉序号下限 | **只有**"诊断含 `entry.sequence-rollback`"转红 | 子代理；主会话复做一次 |
| 篡改 | 验签恒为真 | 篡改信封被接受 | 子代理 |
| 共存 | 恢复 worker 激活时删除本模块的库 | 存储记录消失 | 子代理 |

**撤回场景的变异结果需要说明。** 去掉序号下限后，重放那一步的结果**仍然是 `none`**，转红的只有诊断码断言。原因是已存清单序号为 3，按"取最大序号"它本来就胜过重放的序号 2，所以这个场景里"重放不会被展示"有两层保护，序号下限独有的作用只体现在诊断上。下限不可替代的情形，是已存清单**已经过期**、不再参与选择时，由单元测试"已存清单过期后下限依然有效"覆盖。

## 修订：恢复页的默认样式与宿主定制

规格见[模块规格](../../spec/pwa-entry-resilience.md)的同名修订，交付边界的增补见 [ADR-0018](../../docs/adr/0018-entry-resilience-delivery-boundary.md) 的"2026-09-23 再修订"。分支 `claude/recovery-page-styling`，基于 `main` 的 `52e5035`。每个任务一个提交，提交信息带 `Task: ST<n>`。

### 架构决定

- **class 与样式分两处落地。** class 加在 `src/page/render.ts`（渲染时 `setAttribute("class", …)`，该类型已支持，不改接口）；样式文本在 `src/vite/index.ts` 拼进 HTML。两者由测试对齐：渲染用到的每个 class 都必须在默认样式中出现，反之亦然，避免样式与结构各自漂移。
- **默认样式是模块里的一份独立常量**，不散落在 HTML 拼接代码中，便于审阅与计算哈希。
- **宿主 CSS 原样写入，只挡 `</style`。** 不做 CSS 解析或清洗：那需要引入解析器，且平台无法判断宿主样式的意图。规格已写明宿主自负其责。
- **哈希在 `generateBundle` 阶段算并用 Vite 的 `this.info` 打印**，不写文件——避免再次触发 Cloudflare 部署链路四处白名单的登记要求。
- **观感由人判断。** 自动化只能证明样式存在且变量可覆盖；"大不大气"必须由项目所有者看截图定夺，因此 ST4 明确列为验收环节。
- **执行分工。** ST2 派给 `executor` 子代理；ST3（部署与演示）留在主会话。

#### ST1：规格、ADR 增补与本计划

**验收：** 规格修订节与色值表（`a625b96`、`1b88569`）、ADR-0018 增补已提交；本节随后提交；项目所有者确认后开始 ST2。

#### ST2：样式实现与测试（TDD）

**范围：** `src/page/render.ts` 的 class；`src/vite/index.ts` 的默认样式常量、`css` 选项拼接与哈希日志；`src/vite/options.ts` 的 `css` 校验；对应单元测试与浏览器测试；以及主题跟随：`src/client/index.ts` 新增 `setPwaTheme`，`src/page/main.ts` 在渲染前读取存储键并设置 `data-theme`。

**验收：**
- 渲染后每个元素带规格表中的 class；无多余 class。
- 默认样式包含规格列出的全部变量，亮色定义在 `.pwa-entry`，暗色在 `@media (prefers-color-scheme: dark)` 中重定义同名变量；色值与规格表逐字一致。
- 传入 `css` 时其文本原样出现在默认样式**之后**；未传时文档中只有一段 `<style>`。
- `css` 含 `</style` 时构建失败，报错指出该选项。
- 构建日志输出每段样式的 `sha256-<base64>`，与对该段文本直接计算的结果一致（测试中重算比对）。
- 页面仍无内联脚本；脚本仍是带指纹的外链模块。
- 浏览器测试：断网状态下恢复页的按钮计算样式不等于浏览器默认值（证明样式生效且随文档到达）；宿主覆盖 `--pwa-entry-accent` 后按钮底色随之改变。
- `setPwaTheme("dark"|"light")` 写入 `pwa:theme:<appId>:<environment>`，`"system"` 删除该键；存储不可用时不抛出。
- 恢复页读到该键时设 `data-theme` 并压过系统偏好；读不到、值非法或存储不可用时不设，跟随系统。
- 恢复页**不导入** `client-runtime` 或其他平台包（导入边界测试守住）。
- 既有断言不改；`checkEntryRecovery`、返回路径校验、导航行为不变。

**验证：** 包内 `test` 连续两次、`test:browser`、`typecheck`、`pnpm lint`、`git diff --check`。

**范围估计：** 中，4 个源文件与对应测试。依赖：ST1。

**结果（2026-09-23，已验收）：** 实现见 `ea87a85`；观感复核后追加 `7e5004d`。

复核改了三处，都不是润色：列表项原本自带边框、圆角与底色，内层按钮把三样又重复一遍，读起来是盒子套盒子，现已去掉列表项的全部装饰；`.pwa-entry__button:active` 原本把底色换成 `--pwa-entry-surface`，而文字仍用 `--pwa-entry-accent-fg`，亮色主题下是白字压近白底，改为 `filter: brightness(0.92)`，无论宿主把强调色改成什么都不会压坏对比度；随之 `--pwa-entry-surface` 与 `--pwa-entry-border` 失去最后一个读者——**声明了却没人读的变量是平台兑现不了的承诺**，宿主覆盖它不会有任何效果，因此从样式表与规格色值表中一并删除，色值表剩五项。

新增的 token 对齐测试守住这一类缺陷：声明的每个 `--pwa-entry-*` 必须被 `var()` 读回（反向亦然），声明集合必须与规格色值表逐字相同，两个暗色块必须重定义同一组值。

**变异检查（7 条，全部被测试抓到）：**

| 变异 | 被抓 |
|---|---|
| 多声明一个没人读的变量 | 单元 2 条失败 |
| 两个暗色块给出不同值 | 单元 1 条失败 |
| 渲染用的 class 与样式表不再对应 | 单元 4 条失败 |
| 停用 `@media (prefers-color-scheme: dark)` | 浏览器 1 条失败 |
| 宿主 `css` 不再追加 | 浏览器 1 条失败 |
| 恢复页读错主题存储键 | 浏览器 2 条失败 |
| 删除 `[data-theme="dark"]` 覆盖块 | 浏览器 1 条失败 |

首轮变异有两条是无效的：一条 `sed` 的目标串在源码中根本不存在（`validated.css`），另一条针对的行为只有浏览器测试覆盖而当时只跑了单元测试——两者都表现为"测试没抓到"。**没落地的变异会伪装成覆盖缺口**，因此脚本现在会先断言变异确实改到了文件再跑测试。

**验证：** `typecheck` 通过；包内 `test` 216 项通过（19 个文件）；`test:browser` 的 `styling.spec.ts` 13 项通过；`pnpm lint` 通过；`git diff --check` 无输出。

**验证：** 全仓 `lint`、`typecheck`、`test`、`build` 通过；包内浏览器测试 14 项通过；Spec Guard 文档核验与 main 相同。

## 修订：恢复页的构建期语言与文案覆盖

规格见[模块规格](../../spec/pwa-entry-resilience.md)的同名修订。分支 `claude/pwa-platform-review-cba86f`，基于 `main` 的 `66f4131`；规格提交 `805b05c`。每个任务一个提交，提交信息带 `Task: EL<n>`。与 [vite-adapter 的平台默认离线页](../vite-adapter/plan.md)（任务 OP<n>）同批进行，门禁与评审合并做一次。

### 架构决定

- **文案走已有的配置通道。** 插件把合并后的文案放进虚拟模块导出的配置对象；`src/page/main.ts` 把它传给 `renderPage`；`renderPage` 的签名增加一个 `messages` 参数，所有文案仍只经 `textContent` 写入，占位符在写入前替换。不新增 HTML 解析写入路径，`source-scan` 测试原样约束。
- **内置文案是 `src/page/messages.ts` 中的常量表**，`zh-CN` 一栏逐字等于现有文案，因此默认构建的页面行为不变。
- **页面外壳**的 `lang` 与 `<title>` 在 `src/vite/index.ts` 拼接时写入，`<title>` 经转义；其余外壳文本不变。
- **"未设置时不变"**：改动前后各构建一次 `test/fixtures/app` 并比对。2026-09-24 实测外壳只差脚本指纹，页面脚本与配置脚本字节必然变化（文案改走配置通道），规格已更正为"外壳除指纹外相同、默认文案逐字不变"，对照结果写入验证记录。
- **执行分工。** EL2 派给 `executor` 子代理（sonnet），与 OP2 并行；EL3 浏览器测试留在主会话。
